# Benchmarks

Dated latency results for the registered backends, generated by the reproducible
harness in `portable_attention.benchmark`. Each block carries hardware,
software, and commit context and is appended (newest first).

Regenerate a block with:

```sh
python -m portable_attention.benchmark --threads 1 --commit "$(git rev-parse --short HEAD)"
```

Or compare backends on the same shapes, speedups relative to the first:

```sh
python -m portable_attention.benchmark --backends reference,fused,vulkan \
    --threads default --commit "$(git rev-parse --short HEAD)"
```

## Reading these numbers: cap BLAS threads for multi-head work

Multi-head attention issues many small per-slice GEMMs through NumPy's batched
`matmul`. Under the default OpenBLAS policy (one thread per core) the
thread-synchronization overhead of those tiny GEMMs dominates, so latency can be
**15–25× worse** than with a single BLAS thread (issue #8).

The `fused` backend (`get_backend("fused")`) pins BLAS to one thread internally
for batched inputs and computes in native precision, so multi-head attention no
longer cliffs at default threads — see the newest block below. When calling the
`reference` oracle directly, cap BLAS threads for multi-head workloads instead:

```sh
OPENBLAS_NUM_THREADS=1 python your_script.py
```

The harness pins the thread count for every measurement (via `threadpoolctl`
when installed) and records the process-default configuration in each block, so
the headline numbers reproduce. The thread sweep in each block keeps the
default-threading cliff visible.

Hardware floor for this project: a low-power ARM board (aarch64, 4× Cortex-A76,
8 GB RAM, no discrete GPU).

## 2026-08-19 — commit c6d6ad5 — the Vulkan device path against the CPU backends

**Environment:** aarch64, 4 CPUs. Python 3.12.13, NumPy 2.5.1. portable-attention
0.0.1. `threadpoolctl` 3.6.0.

**BLAS threads (process default, via threadpoolctl):** openblas=4 — no pinning,
which is what a caller gets out of the box.

**Device:** `V3D 7.1.7.0` (Vulkan 1.2.289), the integrated GPU. The backend
plans against the limits the device reports (16 KiB shared memory, 256
invocations per workgroup), which gives a 16×16 tile using 13,440 bytes of
shared memory for the `head_dim=64` shapes below. All device calls in this run
were served by the device — no silent fallback — and the output matched the
float64 oracle to 1.9e-06 on `(1, 8, 128, 64)`.

Regenerate with:

```sh
python -m portable_attention.benchmark --backends reference,fused,vulkan \
    --threads default --commit "$(git rev-parse --short HEAD)"
```

### Backend comparison at default OpenBLAS threads (median over 20 repeats)

| shape (B,H,S,D)  | dtype   | threads |  reference |     fused |     vulkan | fused vs reference | vulkan vs reference |
|------------------|---------|---------|-----------:|----------:|-----------:|-------------------:|--------------------:|
| (1, 1, 64, 32)   | float32 | default |   0.340 ms |  0.126 ms |   0.897 ms |              2.69x |               0.38x |
| (1, 8, 128, 64)  | float32 | default |  69.844 ms |  3.461 ms |  17.610 ms |             20.18x |               3.97x |
| (2, 8, 256, 64)  | float32 | default | 222.196 ms | 24.242 ms | 134.408 ms |              9.17x |               1.65x |
| (1, 12, 512, 64) | float32 | default | 292.713 ms | 69.084 ms | 401.429 ms |              4.24x |               0.73x |

**The device loses to the CPU on this part.** `vulkan` is 5–7× slower than
`fused` on every shape here, and it only beats the `reference` oracle where the
oracle is paying the small-GEMM thread-sync tax (issue #8). The gap widens with
size — 0.90 ms vs 0.13 ms at `(1, 1, 64, 32)`, 401 ms vs 69 ms at
`(1, 12, 512, 64)` — so this is not a fixed dispatch overhead being amortised
away; the kernel itself is slower per element than four Cortex-A76 cores running
OpenBLAS.

That is a believable result for this part rather than a bug: V3D is a small
GPU whose 16 KiB of shared memory caps the tile at 16×16, so the kernel reloads
K and V tiles many times and never gets a large arithmetic block, while the CPU
path hands whole `(S, D) × (D, S)` GEMMs to a tuned BLAS. The V3D data point is
about *portability* — the same kernel and the same conformance kit run on a
device with no CUDA anywhere near it — not about beating the CPU.

**Consequence for `"auto"`:** it keeps routing to `fused`. There is no shape in
the measured range where selecting the device automatically would be right, so
`vulkan` stays opt-in via `get_backend("vulkan")`. Revisit if the tile policy
grows a wider block (more shared memory on another device) or if a backend lands
on a part with a real memory-bandwidth advantage.

## 2026-08-01 — commit db41b9e — full-suite run from a clean checkout

**Environment:** aarch64, 4 CPUs. Python 3.12.13, NumPy 2.5.1 (scipy-openblas
0.3.33, `cortexa57` kernel). portable-attention 0.0.1. `threadpoolctl` 3.6.0.

**BLAS threads (process default, via threadpoolctl):** openblas=4.

Full gate from a fresh clone (`scripts/check.sh`): **187 passed**, **100%**
coverage, ruff/format/pyright-strict/bandit/pip-audit all clean (~11 s).
Install smoke: `uv build` → wheel installed into a throwaway venv → default and
`is_causal=True` calls OK; `available_backends()` → `['fused', 'reference']`;
`get_backend('fused'|'reference'|'auto')` all return correct-shape output.

### Latency by shape (pinned to 1 BLAS thread, median over 20 repeats)

| shape (B,H,S,D)   | dtype   | threads | latency (median) |
|-------------------|---------|---------|-----------------:|
| (1, 1, 64, 32)    | float32 | 1       |         0.172 ms |
| (1, 8, 128, 64)   | float32 | 1       |         5.573 ms |
| (2, 8, 256, 64)   | float32 | 1       |        45.297 ms |
| (1, 12, 512, 64)  | float32 | 1       |       125.923 ms |

### Reference vs fused at default OpenBLAS threads (median over 30 repeats)

| shape (B,H,S,D)   | dtype   | reference | fused     | speedup |
|-------------------|---------|----------:|----------:|--------:|
| (1, 1, 64, 32)    | float32 |  0.168 ms |  0.115 ms |   1.46× |
| (1, 8, 128, 64)   | float32 |  4.241 ms |  2.894 ms |   1.47× |
| (2, 8, 256, 64)   | float32 | 33.895 ms | 22.373 ms |   1.52× |
| (1, 12, 512, 64)  | float32 | 104.61 ms | 64.144 ms |   1.63× |
| (4, 16, 256, 64)  | float32 | 139.63 ms | 89.416 ms |   1.56× |

`fused` stays faster than the `reference` oracle at default threads on every
shape. The *direction* is the reliable result and holds across runs; the
speedup *magnitude* is run-dependent and should not be read as stable — it was
1.9–4.9× in the 2026-07-26 block and 1.46–1.63× here. The difference is driven
by the `reference` numbers, which came in well below 2026-07-26 (e.g.
`(2,8,256,64)` 33.9 ms vs 122 ms; `(4,16,256,64)` 140 ms vs 365 ms) because the
OpenBLAS small-GEMM cliff (issue #8) is load-dependent on a shared low-power
board and was milder this run. This is not a regression: the `fused` latencies
themselves are in line with (and mostly below) prior runs — e.g. `(2,8,256,64)`
22.4 ms vs 24.9 ms, `(1,12,512,64)` 64.1 ms vs 79.4 ms — so absolute fused
performance held or improved. No regressions filed.

## 2026-07-26 — commit e55387f — fused backend removes the default-thread cliff

**Environment:** aarch64, 4 CPUs. Python 3.12.13, NumPy 2.5.1 (scipy-openblas
0.3.33). portable-attention 0.0.1. `threadpoolctl` 3.6.0.

**BLAS threads (process default, via threadpoolctl):** openblas=4. Both backends
are measured at the **process-default** thread count (nothing pinned by the
harness) — this is what a user gets out of the box, and where the reference
multi-head cliff appears. The `fused` backend pins BLAS to one thread internally
for batched (multi-slice) inputs; `reference` does not.

Reproduce this block with the harness API (the `--threads 1` CLI at the top of
this file pins BLAS and measures the pinned suite instead):

```python
from portable_attention.benchmark import benchmark_shape

for backend in ("reference", "fused"):
    r = benchmark_shape((2, 8, 256, 64), threads=None, backend=backend, repeats=30)
    print(backend, r.latency_ms)
```

### Reference vs fused at default OpenBLAS threads (median over 30 repeats)

| shape (B,H,S,D)   | dtype   | reference | fused     | speedup |
|-------------------|---------|----------:|----------:|--------:|
| (1, 1, 64, 32)    | float32 |  0.171 ms |  0.119 ms |   1.44× |
| (1, 8, 128, 64)   | float32 |  6.518 ms |  3.388 ms |   1.92× |
| (2, 8, 256, 64)   | float32 | 122.04 ms | 24.910 ms |   4.90× |
| (1, 12, 512, 64)  | float32 | 289.71 ms | 79.437 ms |   3.65× |
| (4, 16, 256, 64)  | float32 | 365.32 ms | 107.30 ms |   3.40× |

The multi-head shapes no longer cliff at default threads: `fused` is 1.9–4.9×
faster than the `reference` oracle without the caller needing to touch
`OPENBLAS_NUM_THREADS`. The single-slice `(1,1,64,32)` case is left unpinned
(pinning a lone sub-millisecond GEMM is not worth the thread-pool reset cost),
so it is still slightly faster purely from native-precision compute. Absolute
numbers are noisy on a shared low-power board; the cross-backend ratios are the
stable signal.
